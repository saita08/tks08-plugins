# 4ldk

> 「このロジック、どこに置きましょうか」
> 「前の現場と同じで」
> 「前の現場を知りません」
> 「……その前の現場は」
> 「それも知りません。毎朝、初出勤です」

個人開発者は一人親方です。設計も施工も検査も、施主への言い訳も、全部ひとりでやります。施主も自分です。そして親方の頭の中には、どの家にも使う間取りがもう決まっています。図面に起こしたことは一度もありません。自分が知っていれば足りたからです。

ところが、毎朝やってくる腕のいい職人が、前の現場のことを何ひとつ覚えていない。腕は確かなのに、玄関をどちらに向けるかから毎回聞いてくる。三軒目あたりで親方は気づきます。これは打ち合わせではなく朗読だ、と。

`4ldk` は、その間取りをついに図面に起こしたものです。`models` `controllers` `services` `repositories` の四部屋に、views の `pages` `components` `parts` が L、D、K。親方の家は、どの現場でも 4LDK です。施主の希望は聞きます。聞いたうえで 4LDK です。

## 物件概要

| | |
|---|---|
| 間取り | 4LDK(納戸、玄関つき) |
| 構造 | 在来工法。Fowler の Service Layer と Repository、オニオンアーキテクチャの依存の規律、Atomic Design を 3 層に緩めた View |
| 動線 | 外から内への一方通行。逆走不可 |
| 配電盤 | 一箇所(エントリ) |
| 増築 | `mcp/` `auth/` `gateways/` `lib/`。必要が現実になった時点で応相談 |
| 対象 | 単一のデプロイ対象に収まる小〜中規模のプロダクト |
| 告知事項 | `GoalService` という名前の部屋は建てられません |

工法に独自のものは一つもありません。どれも築数十年、風雪に耐えた在来工法です。一人親方に、新工法の実験台になる余裕はありません。倒れたとき、支えてくれる同僚がいないので。

## 内見

**models(奥の間)。** エンティティの型と、エンティティ固有のルールだけが置いてある部屋です。DB も DOM も知りません。何にも依存しません。土足厳禁で、ライブラリの持ち込みも原則お断りしています。この部屋がきれいなおかげで、サーバー側の各部屋と views が、ビルドの境界をまたいで同じ型を見られます。

**controllers(応接間)。** 客の用件を聞き、形式が整っているかを確かめ、奥へ取り次ぎ、返事を客に分かる形に整えて返す。それだけの部屋です。ここで料理を始めてはいけません。応接間で煮炊きをする家は、だいたい後で揉めます。

**services(仕事部屋)。** 仕事は全部ここでします。HTTP から来た客も MCP から来た客も、同じ仕事部屋に通されます。部屋は機能ごとに分けます(繰り越し、レビュー、判定)。エンティティごとには分けません。`GoalService` という名前の部屋は、Goal と名のつく荷物を全部呼び寄せて、半年後には開かずの間になるからです。複数の機能が共有するエンティティのルールは、奥の間へ。同じルールを二つの部屋に写し始めたら、置き場を間違えた合図です。

**repositories(蔵)。** SQL と外部ストレージの知識は、全部この中です。蔵の匂いを母屋に出さない。仕事部屋は、蔵に何がどう積んであるかを知りません。欲しいものの形だけを伝え、蔵がそれに合わせて出してきます。

**views(LDK)。** ここだけブラウザ向けビルドを通ります。客を通すリビングが `pages/`(ルーティング単位)。料理を意味のある一皿に盛り付けるダイニングが `components/`(ドメインを知っている)。誰の家に持っていっても使える鍋と包丁の並ぶキッチンが `parts/`(ドメインを知らない)。

仕分けの問いは一つだけです。この部品はドメインを知っているか。一問で終わるので、これは atom か molecule かで午後が溶けることはありません。親方は化学の時間に寝ていました。なお、鍋に施主の名前を彫った時点で、その鍋はダイニング行きです。

**玄関と納戸。** views からサーバーへ出入りする戸口は `views/api/` の一つだけで、fetch はここにしかありません。窓から出入りする家族がいると、防犯上も設計上もよくない。画像やフォントは納戸の `assets/` へ。

## 動線

住宅設計で一番大事なのは動線だ、と親方は言います。この家の動線は、外から内への一方通行です。

- 入口(controllers、mcp)は services を呼ぶ。services は入口を知らない。入口が入口を呼ぶことはない。応接間から隣の応接間へ客を回す家はありません
- 境界の型は、使う側の services が決める。repositories と gateways がそれに合わせる。インターフェースだけのファイルは、差し替えが現実になるまで書かない
- services は repositories を import しない。実装は引数で受け取り、組み立てて渡すのはエントリの一箇所だけ。配電盤が一つなら、ブレーカーが落ちたとき探す場所も一つで済みます
- 検証は二段。形式は入口で、業務ルールは services で。エラーも同じ分界で、services はドメインのエラーを投げ、HTTP ステータスへの変換は入口がやる
- ライブラリは、それが体現する知識の住む部屋に属し、その型を部屋の外に漏らさない。変換のためだけの部屋は建てない。廊下のためだけの廊下は要りません

目的は、変更の波及を止めることです。DB の差し替えは蔵で止まり、UI の刷新は LDK で止まり、入口の追加は仕事部屋に触れない。水回りを直すたびに居間の床まで剥がす家を、親方は二度と建てたくないのです。

## 増築について

`mcp/` のような入口、`auth/` のような入口の手前に挟まる横断層、ネットワーク越しの外部サービスのための `gateways/`、どの部屋の知識でもない無色の共通関数のための `lib/`。どれも、必要が現実になったときにだけ建て増します。いつか使うかもしれない部屋は、だいたい物置になります。特に `lib/` は、油断すると家中の「とりあえず」が流れ着く部屋なので、各部屋の検問(エンティティのルールか、業務の手順か、画面の道具か)を全部通らなかったものだけを入れます。

## 使い方

図面を読ませるのに、操作は要りません。「いつものアーキテクチャで始めて」と言うか、このコードをどの部屋に置くかという話を始めると、Claude が読み込んで従います。

規則を破る依頼をしたときは、黙って従わず、どの規則にどんな理由で触れるかを先に伝えます。断りもしません。決めるのは親方です。ただ、知ったうえで外すのは設計変更で、知らずに外れるのは施工ミスです。請求書の宛先が違います。宛先はどちらも自分ですが。

### `/4ldk:scaffold`

上棟です。プロジェクトに骨組みを建てます。四部屋と LDK は必ず、増築分は必要がすでに現実であるものだけ。建てるものの一覧を先に見せ、承認されてから建てます。既存のファイルには触れません。サンプルのエンティティも置きません。モデルルームの家具は、結局ぜんぶ捨てることになるので。

最後に、このプロジェクトがこの図面に従うこと、いま建っている部屋と見送った部屋を短い文書に残します。次に来た職人は、説明なしで同じ規則に従えます。どうせ何も覚えていないので。

### `/4ldk:check`

竣工検査、あるいは築半年の定期点検です。既存のツリーを図面に照らして見て回ります。

import を読めば決まる機械的な違反(動線の逆走、入口から入口への取り次ぎ、仕事部屋が蔵の鍵を自分で持っている、玄関以外からの fetch、奥の間を覗いているキッチンの鍋)と、読んで判断する所見(エンティティ名の部屋、応接間で始まっている煮炊き、部屋の外へ漏れたライブラリの型、二つの部屋に写されたルール)を分けて報告します。各所見にはファイルと行、破っている規則、それによってどの変更が波及するようになったかが付きます。

直しはしません。検査員は金槌を持ってきません。意図した設計変更か施工ミスかを言えるのは、建てた本人だけだからです。たいてい本人ですが、たいてい覚えていません。だから行番号を付けてあります。

## 向かないもの

4LDK は一軒家の間取りです。一つのデプロイ対象に収まる、小〜中規模のプロダクトを想定しています。

プロダクトを複数のサービスに分けて別々にデプロイする規模や、チームで分業するためにモジュールの境界を契約として固める必要がある規模は、この図面の範囲の外です。その兆候が見えたら、Claude は 4LDK を無理に引き伸ばさず、そう伝えます。

一人親方の図面でビルは建ちません。ビルを建てる日が来たら、まずは人を雇ってください。おめでとうございます。
